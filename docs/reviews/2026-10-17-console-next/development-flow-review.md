# 新版研发交付流程评审与多视图设计

开发交接入口：[设计规格](../../superpowers/specs/2026-10-17-development-delivery-design.md) · [实施任务](../../superpowers/plans/2026-10-17-development-delivery-implementation.md)。接手开发以这两份文档为准，本文件保留问题证据。

日期：2026-10-17。范围：新版 `/next/`、经典版交付入口对照、当前流水线模型/引擎/模板。仅新增评审文档，未修改业务代码、触发流水线、审批、合并或部署。

## 结论与证据边界

“产品提供上下文、服务负责运行、交付管理过程”的方向合理，默认运行记录也比把所有管理卡片堆在同页容易理解。但新版尚有操作回退、决策入口不匹配、发布产物未锁定和证据缺失，不能认为完整研发交付闭环已经迁移完成。

本次核对当前 dirty tree 的源码；其他 agent 正在修改服务运行部分，本评审不动其文件。浏览器实际处于登录过期状态，点击本地提供的 Acme 演示管理员入口后显示“登录失败”，未继续尝试其他凭证。因此：以下“已确认”指源码路径确认，不代表已完成真实流水线、浏览器视觉或集群验收；视觉部分为基于组件结构、样式和交互的设计评审。

## 一、优先修复的缺口

### F1 · P1：金丝雀等待阶段没有正确决策入口

证据：`frontend/console-user-v2/src/views/RunDetail.vue:62` 与 `:128`，任何 paused run 都显示“通过审批”并调用 `approveStage`；`internal/devops/pipeline/engine.go:958` 明确拒绝通过通用 Resume 恢复 canary。独立 `canaryDecision` 已在新版 `src/api/pipeline.ts` 暴露，但未被运行详情使用。经典版 `frontend/console-user/src/views/app-tabs/PipelineRunView.vue:72`、`:145` 已分别处理 canary 观察和 promote/terminate。

影响：用户在金丝雀等待点无法从新版完成放量决策；人工测试也被叫成审批，容易误解。

设计：按当前 stage 类型显示“确认测试结果”“批准/拒绝上线”“确认放量/终止验证”；金丝雀决策区同时展示实际目标、基线与候选版本、验证入口、指标来源和缺失情况。“终止运行”和“拒绝审批”要有不同理由与结果说明。

### F2 · P1：变更与批次有查看入口，缺少组织入口

证据：新版 `DeliveryChanges.vue` 只导入列表、集成、审批、发布 API；全 `src/` 中 createChange/createBatch/addChangeToBatch/removeChangeFromBatch 只在 API 文件定义，没有页面调用。经典版 `AppChanges.vue:89`、`:283` 已有创建变更、创建批次并加入成员。新版 `ChangeDetail.vue:90` 仍提示去“变更 tab 创建批次并入批”，实际没有这个按钮。

影响：人工研发路径被削弱；已有变更也无法在新版完成组批或冲突后移出。

设计：变更列表主操作“新建变更”，支持关联已有分支/创建分支与人工或 Agent 两种执行方式；选择多个可入批变更创建批次；批次内支持顺序、增删、冲突项定位和移出。简单单服务变更可直接验证，不强迫所有交付先理解批次。

### F3 · P1：审批与实际发布产物之间存在漂移风险

证据：`internal/devops/pipeline/templates.go:55` 默认 CD 先 approve，后 canary，canary 的 imageSource 为 latestReady；AI 交付模板 `:99` 同样使用 latestReady。`engine.go:1153` 在执行该 stage 时调用 LatestReadyImage；`cmd/core/pipeline_adapters.go:226` 只按应用取第一个 ready 镜像，未限定本次构建/提交/服务。

影响：审批等待时另一个构建完成，可改变实际选择的镜像；同产品多服务时也缺少足够的产物归属保证。此处是由当前默认路径推导出的风险，本次未制造并发运行复现。

设计：在审批前解析并固化 `serviceId + repoId + commitSHA + imageId + digest + sourceBuildRunId`，由测试到生产晋升同一 digest。AI 同次交付优先引用本次前序构建产物；独立 CD 必须显式选候选产物，展示其测试证据。审批、重试、canary、正式部署都引用该快照，不在后续 stage 重新选 latest。门禁或候选版本改变应使既有审批失效。

### F4 · P1：流水线配置无法表达新版默认 CD 的关键目标

证据：`PipelineDesigner.vue:58` 只筛选 type=deploy 展示环境/服务参数；默认 CD v3 已改为 approve→canary→release→baseline，canary 没有相应参数区。手动运行弹窗 `DeliveryPipelines.vue:108` 只有分支输入和“按配置执行”的通用提示。

影响：用户无法从弹窗看出实际发布哪个服务、哪个环境、哪个镜像；多服务应用无法可靠配置 canary 目标。

设计：阶段参数由阶段类型/schema 驱动，覆盖 canary 和 agent 等类型；运行前增加只读执行计划预览，展开模板默认值与覆盖值的最终解析结果。服务、仓库、环境、镜像使用选择器，保留模板约束。无法解析的目标阻止执行；不要求租户用户手改阶段索引或内部 ID。

### F5 · P1：质量结果被压缩为泛化“测试通过”

证据：`engine.go:626` 的 test 目前是 smoke/manual，smoke 在显式路径失败后可自动回退 `/`（`:660`）。新版没有独立单测/覆盖率/安全扫描结果结构；构建脚本自身是否执行过这些检查不能仅靠此 UI 判断。

影响：根页面 HTTP 成功可能被误认为预定健康检查成功；冒烟、人工确认与业务验收的证据不够清晰。

设计：分别展示构建、指定探活、自动化测试、人工验证、AI 验收和发布后观察。检查结果至少有类型、目标、预期、实际、时间、执行版本、报告链接和 pass/fail/unknown。探活回退必须显式配置并标注实际使用路径；生产关键检查默认严格按指定条件判定。缺少报告显示“未配置/未验证”，不能绿色通过。

### F6 · P2：运行页未形成产物与运行证据的连续导航

证据：`RunDetail.vue:159` 阶段说明只优先显示 error/branch/waiting；展开区只有事件 log 与构建日志链接。releaseId、workloadId、imageId、canaryDomain、Agent run 等已有输出未结构化展示；经典版 `PipelineRunView.vue:394` 已有 outputEntries 链接化。

设计：每个阶段有“结果、日志、输入、输出、关联资源”；构建→镜像，部署→精确工作负载/实例事件，探活→目标地址和检查记录，Agent→工作区/提交/审查/验收，发布→发布单和回退。默认打开失败或等待决策的节点，保留 URL stage 定位。

### F7 · P2：状态与时间线存在误导

- 后端 `model.go:46` 阶段成功是 `succeeded`，新版 `useStatus.ts:106` 只映射 `success`，且缺 aborted；成功阶段会回显原文并使用中性色。应由契约统一枚举，waiting 还需按阶段类型派生中文。
- `ChangeDetail.vue:114` 用同一 updatedAt 生成入批、测试、上线多个事件；abandoned 也满足 status != open，可能生成并未发生的“入批集成”。应使用真实事件；历史数据不足时仅显示当前状态/最后更新时间。
- `RunDetail` 只在首次挂载和操作后 schedule，轮询终态后未主动停止；同路径切 runId 没有 watch/请求序号，存在旧目标信息残留风险。需完善终态停止、切换重置和响应竞态保护。
- `BuildDetail` 把任意请求失败呈现“构建不存在或已删除”；需区分 403、404、服务异常、日志流断开与无日志，不能把网络问题解释为资源被删。

### F8 · P2：交付中心的待办更像通知历史

证据：`Delivery.vue:44` 仅按 severity 排除 info，没有逐项验证事项当前是否仍待处理；是否过滤已解决取决于后端返回，当前前端不能证明。

设计：显示待办类型、责任人/是否我可处理、当前阻塞、等待时长、具体动作；基于实体当前状态去除已解决项。保留“全部通知”作为独立历史，不让陈旧警报重复占用值班注意力。

## 二、保留的组织与需要调整的入口

保留：全局交付中心聚合待办与执行，产品内负责上下文操作；运行、配置、发布的概念隔离；模板+参数覆盖的治理模式；已有构建日志 SSE、发布记录和回滚接口。

产品交付目前并列七项：运行记录、智能研发、变更与批次、流水线、构建与镜像、发布、代码仓库。建议按任务明确归属，在同一工作区内分组，保留旧 query 链接映射：

```text
交付概览：待我处理、当前执行、各环境版本、下一步
变更：人工变更、Agent 变更、批次（按需）
流水线：定义与配置 → 某条流水线详情 → 运行记录
发布：候选产物 → 环境晋升 → 发布记录/回退
代码与产物：仓库/PR、构建、镜像（辅助入口）
```

智能研发作为“创建变更”的一种执行方式，保留便捷入口，同时和人工研发共享变更、验证及发布标准。范围选择改为“生成代码 / 验证到测试 / 发布到生产 / 标记版本与合并”四个明确里程碑，运行前展示实际阶段与目标。避免当前“上线验证”“版本发布”的勾选组合让用户猜测哪一步已经影响生产。

## 三、流水线多视图：建议做，按任务分层

| 视图 | 所在层级 | 回答的问题 | 建议优先级 |
|---|---|---|---|
| 定义/运行列表 + 迷你阶段条 | 流水线目录、某流水线运行历史 | 哪条失败、最近做了什么、谁触发 | 第一批 |
| 阶段流程图 + 侧边详情 | 单次运行，默认视图 | 到哪一步、卡在哪里、下一步怎么处理 | 第一批 |
| 步骤列表 | 单次运行，可切换 | 小屏和键盘如何逐项检查，所有输入输出是什么 | 第一批 |
| 耗时视图 | 单次运行的二级视图 | 哪个阶段耗时、等待审批还是实际执行慢 | 第二批 |
| 服务 × 环境版本矩阵 | 产品发布/交付概览 | 哪个环境运行哪个 digest，是否同一候选版本，能否晋升 | 第二批 |
| 变更看板 | 多个变更或批次 | 哪些待开发、待验证、阻塞、待发布 | 按需求后续 |

这六项不是同一页面上的六个视图按钮。用户在不同层级看到对应的 2–3 个选择；列表、图和耗时共用同一 run/stage 数据与动作解析，不复制状态机。

重要边界：当前 `StageDef` 只有 name/type/params；引擎依 currentStage 顺序执行。第一期画真实的线性阶段图，保留清晰的方向与状态。只有后端有 dependsOn、条件、分支、并行汇合和节点级重试语义后，才绘制并允许编辑 DAG；不能用画布连线暗示已支持并行执行。

## 四、单次运行页面布局

```text
产品 / 流水线名称 / 本次运行
需求标题、分支、commit、操作者、触发方式、时间
服务 · 环境 · 泳道 · 候选 digest · 模板版本 · 观测时间

正在等待：生产上线审批         [查看验证证据] [批准] [拒绝]
审批理由、实际影响、允许操作的人和超时策略

[流程] [步骤] [耗时]                         刷新/自动更新状态
检出 → 构建 → 测试泳道 → 冒烟 → 上线审批 → 金丝雀 → 版本 → 主干同步
                  当前选中节点 ───────────────┐
                                            │ 节点详情
下方/右侧：结果 | 日志 | 输入输出 | 关联资源    │ 实际目标、证据和操作
```

上述是通用设计示意，具体节点必须来自该次运行快照；不能为不存在的检查补出假节点。canary 内展开“部署候选→观察→决定→基线滚动”，只有接口返回实际子状态才能展示子步骤完成，否则保留阶段说明。

视觉重点：

- 页头使用可理解的任务/流水线名称，run ID 降为辅助信息并可复制；重点展示业务目标和当前阻塞。
- 只有一个当前主操作，审批/放量确认区紧邻证据；删除收进“更多”，不与运行按钮同权重。
- 阶段节点同时有文字、图标、状态色，成功、失败、等待、跳过、未验证各自清晰；不能只靠红绿识别。
- 宽屏图+详情，1024 以下优先纵向步骤；390px 无页面级横向溢出，日志区域独立滚动。
- 阶段耗时区分执行和人工等待；没有排队事件的旧运行不虚构排队时间，缺时间字段显示未知。
- 点击节点保留选中位置，日志自动跟随可暂停，失败和断线提示置于正文外；图和表都能键盘访问。
- 切换视图保留 run、stage、筛选和滚动语义；URL 支持 `view=graph|steps|timing&stage=...`，旧 run URL 不变。

## 五、发布矩阵与证据模型

矩阵是跨运行、跨环境的聚合视图，独立放在产品交付概览/发布下：

| 服务 | 测试 | 预发布（如有） | 生产 |
|---|---|---|---|
| 示例 api | commit A / digest X / 已验证 | 未部署 | digest W / 正在运行 |
| 示例 worker | digest Y / 验证中 | 未配置 | digest V / 观测过期 |

以上仅展示设计字段，不是真实资源数据。单元格展开部署时间、泳道、发布单、验证证据、运行观测和晋升/回退能力；矩阵默认基线，预览泳道单独筛选。生产格显示观测版本与期望版本，读取失败不写“未部署”。回退产生新操作/发布记录，不改历史记录冒充恢复成功。

支撑多视图的增量信息：

- `resolvedTargets`、`artifactSnapshot`、模板版本/定义哈希、配置快照、报告列表。
- stage 稳定 ID 或不可变 run 内 index、动作能力与原因、检查类型/结论、真实事件时间、retry attempt、错误与资源引用。
- 请求级执行计划预演：返回最终解析结果和缺配置项；服务器执行时固化并复验，防止预览到运行之间目标漂移。
- 若要求生产独立审批，增加结构化审批决定、审批人/时间/理由与可配置禁止自审；已有审计记录和 prod:write 必须保留，不能把本建议理解为当前完全没有权限检查。
- 运行间取消/排队策略按服务×环境×泳道核实，当前每条 pipeline 的 active-run 限制并不自动证明不同流水线不会竞争同一个目标；没有完成这项核实前，不在图上承诺并行安全。

## 六、建议实施顺序与验收

1. 先恢复 F1/F2 操作闭环，锁定 F3 发布产物，补 F4 执行计划与配置；同步修复枚举和假时间线。
2. 对现有 RunDetail 增加流程视图、步骤详情和证据导航；单一状态/动作映射供所有视图使用。
3. 增加候选产物晋升与环境版本矩阵；耗时图随后补齐，不急于自由拖拽设计器和变更看板。
4. 再补结构化测试报告、自动化发布观察、审批策略、跨流水线目标互斥与更复杂 DAG。各项按真实实现启用。

必须回归：人工变更创建/入批/移出；冲突修复后重新集成；人工测试确认；普通审批；canary 放量与终止；两个服务各自镜像；等待审批时新构建完成；重试沿用锁定产物；发布成功但主干合并失败；拒绝/撤权；读取异常；同路由切换不同 run；390/768/1024/1440px 和亮暗主题。

用户体验目标：有完整配置时测试部署 ≤5 次主要动作、≤2 次页面切换；从失败阶段到日志或实例事件 ≤2 次动作；审批面直接回答“谁的什么版本将部署到哪里、依据什么通过、失败如何恢复”。截图、构建通过和流程图动画不替代真实集群验收。

## 官方设计依据

- [GitLab pipeline editor](https://docs.gitlab.com/ci/pipeline_editor/)：配置与可视化关联，并可校验配置；这里借鉴信息呈现，不要求引入 GitLab 或复制其执行模型。
- [GitHub reviewing deployments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/review-deployments)：审批/拒绝与环境保护规则、禁止自审可配置。
- [Argo Rollouts analysis](https://argo-rollouts.readthedocs.io/en/stable/features/analysis/)：将采样、成功/失败条件和分析结论用于继续、暂停或中止发布。当前仓库的并行验证泳道不等于已具备百分比流量切换和指标自动回退。
