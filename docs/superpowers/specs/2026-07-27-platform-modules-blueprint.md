# 平台模块蓝图

> 一站式 PaaS 平台的模块全景与路线图。CLAUDE.md 定位：服务治理 / 中间件管理 / MaaS / DevOps 四大子系统 + Platform Core 底座。
> 本文是产品全貌锚点：新模块归属、切片优先级、贡献者认领，都从这里对齐。

## 信息架构原则

「资源」在 PaaS 里被滥用，本项目严格区分三个正交维度：

| 维度 | 本质 | 实例 | 是否可绑定应用 |
|---|---|---|---|
| **数据服务**（资源中心） | 有实例 / 有连接信息 / 独立生命周期 | DB / 缓存 / MQ / 模型推理 / 对象存储 | ✅ Add-on |
| **工作负载** | 应用自身运行形态 | 服务 / Job / CronJob | ❌ 是应用本身 |
| **平台能力**（横切） | 所有应用共享 | 治理 / 可观测 / 安全 | ❌ 平台级 |

判断口诀：**能否「申请一个实例绑定到某个应用」？能→数据服务；不能→工作负载或平台能力。**

## 模块全景

```
Platform Core（底座 · 所有子系统依赖）
  ✅ 插件机制（Registry 拓扑排序 + 环检测 + 依赖倒置）
  ✅ 身份骨架（Tenant / User / Role / APIKey / 内存仓储）
  ✅ 多租户隔离（ctx 传播 + Repository 强制过滤 + API Key 解析租户）

  ❌ 组织树 / 工作空间隔离
  ❌ 配额与计费（多租户商业化根基）
  ❌ 事件总线（NATS 嵌入式）
  ❌ 审计日志

应用（主线）✅
  ✅ 生命周期 + 资源绑定（绑定/解绑端到端）
  ✅ 多租户隔离（TenantID + Repository 强制过滤）
  ❌ 应用配置（env/Secret tab）
  ✅ 工作负载编排（Service/Job/CronJob 领域 + API + 视图，mock）

资源中心（数据服务 Add-on）
  ✅ 模型推理 MaaS（Model→Channel→Provider 三层）
  ❌ 数据库 RDS / 缓存 Redis / 消息队列 / 对象存储 / 向量数据库 / 搜索引擎

工作负载 ✅
  ✅ Service/Job/CronJob 领域 + 跨应用视图 + 应用详情部署 tab（mock）
  ❌ K8s 真实编排 / 日志事件 / HPA / 灰度
  服务 Deployment / 任务 Job / 定时 CronJob / 函数 FaaS*

DevOps ❌
  CI/CD 流水线 / 制品镜像仓库 / 发布编排（蓝绿/灰度/金丝雀）/ 回滚

平台能力（横切）
  ❌ 服务治理：注册发现 / 配置中心 / API 网关 / 熔断降级
  ❌ 可观测：指标监控 / 日志聚合 / 链路追踪 / 告警
  ❌ 安全：密钥 Secret / 证书 / IAM 访问控制 / 网络防火墙 / 合规审计
```

## 关键概念澄清

### 配置中心 vs 应用配置

| | 应用配置 | 配置中心 |
|---|---|---|
| 归属 | 应用详情 → 配置 tab | 平台能力 → 服务治理 → 配置中心 |
| 形态 | env / Secret，工作负载启动注入 | 运行时动态配置，跨实例共享 |
| 更新 | 改了要重启/重新发布 | 热更新，无需重启 |
| 能力 | 键值对 | 版本 / 灰度 / 回滚 / 客户端监听 |

两者不冲突，是不同层面。配置中心归治理四件套，不单独顶级菜单。

### Job 不是资源

Job / CronJob 是应用的工作负载形态（应用以什么方式跑），不是可绑定的外部资源。归「工作负载」，在应用详情的部署视图与跨应用的工作负载视图都能看到。

## 切片优先级（路线图）

按「不做就不算完整 PaaS」与依赖关系排序：

1. ~~**身份与 RBAC** — 多租户隔离根基，Core~~ ✅ 已落地
2. ~~**工作负载** — 没有它应用只是个壳~~ ✅ 已落地（mock）
3. **DevOps CI/CD** — 代码到上线主链路
4. **服务治理**（含配置中心）— 微服务核心
5. **可观测** — 运维必备
6. **安全** — 密钥/证书/IAM
7. **配额计费** — 商业化
8. **数据服务资源** — DB/缓存/MQ/存储/向量/搜索（逐个接）
9. **真实 vLLM 纳管 + K8s 编排** — MaaS 数据面落地

当前：✅ Core 骨架 + 多租户身份骨架（RBAC + 隔离）+ MaaS（mock）+ 应用主线 + 工作负载（mock，约 35%）。

## 架构约束（不变）

- 三层 + 插件：Platform Core 最小内核 + 插件化子系统（子系统是插件，非独立微服务）
- 数据面与控制面解耦：控制面下发期望状态，数据面执行
- Core 不依赖外部治理/中间件（避免元设施鸡生蛋）
- 业务领域逻辑绝不进 Core（判断：「MaaS / 治理 / DevOps 都会用吗？」）
- 多租户隔离由 Core 统一治理，插件不得绕过
- 全开源 Apache 2.0，CI 禁 GPL/AGPL
