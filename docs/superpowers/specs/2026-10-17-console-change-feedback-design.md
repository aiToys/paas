# 专项 04：配置、流量、环境与可观测的结果反馈

状态：设计交接。对应 CF-01/02、OB-01、GV-01、UX-01/02；继续复用现有运行与泳道设计。

## 1. 设计边界

四个领域共享“目标明确、期望与观测分开、失败可定位”的展示语言；各领域保留自己的 API、控制器与状态机。配置发布、Ingress 下发、采集健康、环境删除不能归并成一个万能操作后端。

当前动态配置已有 diff、发布历史、服务端合并预览、泳道覆盖及提升，不再新增重复编辑器。当前可观测已有完整五区和 TraceID 直查，不再搭建平行大屏。

## 2. 配置的信息架构

产品 → 配置：启动配置 / 动态配置；全局配置中心：共享命名空间与跨产品引用。局部配置环境可独立于顶栏浏览范围，但必须在页头写出“正在编辑：产品A / 测试环境 / 泳道feature-x”。

原有 `envId=''` 兼容配置不能再仅称“基线”，建议显示“默认配置（兼容/继承源）”；具体环境下的 lane=default 称“环境基线”。UI、发布确认、审计和导出的命令都采用同一含义，避免两种“基线”混淆。

```text
产品配置      编辑目标：测试环境 / feature-x       [查看有效值]
草稿 3 项变更     已发布配置 v12     客户端采用情况：未知
Key | 来源（共享/产品/泳道） | 已发布值 | 草稿值 | 变更类型
───────────────────────────────────────────────────────────
发布预览：测试 / feature-x · 新增1 修改1 删除1
影响：2个服务 · 覆盖语义：整批提交 · 需要确认：无消费者回报能力
                           [取消] [提交此次变更]
```

共享引用以来源链解释，值相同也保留来源；敏感值只比较是否变化，不向浏览器提供明文 diff。运行时配置的新增/删除与取消覆盖分开：

| 操作 | 必须解释的结果 |
|---|---|
| 修改泳道覆盖 | 覆盖当前 key 的最终值 |
| 移除泳道覆盖 | 恢复继承下层来源，不等于删除最终配置 |
| 删除有效 key | 需要明确 tombstone/删除语义，兼容层不支持时阻止并解释 |
| 提升到基线 | 展示覆盖集与目标环境基线的 diff；排除并发漂移，不改变其他环境 |

## 3. 配置变更的提交与生效

首期必须停止把逐 key 写入概括成一个不可区分结果。当前 confirmPublish 串行 upsert，任一中间失败会留下已写入 key；新增 key 还会改基线草稿。改进分两层：

- **前端立即改进**：固定提交目标与输入快照，记录逐项结果，失败保留成功/失败/未执行列表；不显示整批成功，不盲目重发全部 key；发布期间禁止切目标覆盖结果。明确哪些操作改变了基线草稿。
- **后端目标契约**：一次提交变更集，含 target、expectedRevision、增改删操作、idempotencyKey；在同一领域内事务写入并生成 revision/audit。冲突返回 409 与重预览入口。原逐项 API 保持兼容，新客户端优先批次接口。

期望状态链为“草稿 → 配置已发布 → 客户端拉取/采用”。没有客户端上报就展示“已发布，采用情况未知”，不能根据 HTTP 2xx 或时间流逝自动显示“全部生效”。可选后续增加 consumerId、版本、最后心跳、采用时间；遥测可能延迟或缺失，分母与覆盖率要可解释。

启动配置保存后展示“待重建注入”及受影响工作负载，链接已有运行操作；用户显式发起 rollout 后，根据操作记录/Pod 配置版本核验。不能保存配置后自动重启所有服务。

## 4. 流量治理

保留对外路由/服务目录/熔断三个分区。路由默认行展示 host/path、目标服务、环境/泳道、配置启停、下发状态、最近检查。详情打开“配置 → K8s 对象 → 外部入口”三层证据：

1. 已保存/期望启用；
2. 已下发或协调失败，附相关对象与 controller 错误；
3. DNS/TLS/HTTP 探测结果与时间，仅在后端实际探测可用时提供。

未探测就写未检查，不把 enabled=true 显示为公网可达。路由预览展示命中路径、目标端口、冲突与环境；TLS/证书信息来自真实 Ingress 配置，不默认承诺证书托管。熔断策略“配置启用”“实际评估窗口/样本”“实时状态”分别显示，无样本不判定业务健康。

服务实例标明 Endpoints 发现或手工注册；数据面发现实例不提供看似能长期改变真源的手工心跳/注销入口。发现与工作负载 Pod 关联有证据才链接，名称相近不构造关联。

泳道域名沿用业务入口/联调入口/内部地址分区；展示域名可达性与全链路染色是两种验证，打开浏览器 URL 不证明请求已携带 lane header 或 SDK 传播成功。地址接口失败应显示独立错误条，不能整个访问区消失。

## 5. 可观测：采集覆盖与数据质量

当前指标、日志、TraceID 已可达；本专项优先回答“为什么没有数据”。现 real metrics 的部分失败被 log+continue 吞掉，需要结果质量契约，否则前端错误面板无法准确提示。

| 结果状态 | 呈现与下一步 |
|---|---|
| 未接入 | 采集源未配置；按角色提供接入说明，保留其他已接入信号 |
| 查询成功，无数据 | 时间范围、目标、exporter/埋点检查；不画零值，不报平台故障 |
| 部分结果 | 保留成功指标，标缺失实体/信号、原因与读取时间 |
| 源不可用/查询失败 | 错误信息及重试；旧数据可保留但标过期，不显示“全部健康” |
| 真实零值 | 正常绘制 0，区分于缺采样点 |

API 提案：兼容返回 series，并提供可查询的 quality 元数据（source、observedAt、requestedTargets、successfulTargets、warnings）。可采用新增响应类型或附属诊断端点，不能直接破坏现有 list 数组契约。全失败应返回可识别错误，部分成功带警告；上游敏感 URL/凭证不回传。

指标页增加“采集覆盖”折叠区：实体×基础资源/RED/业务指标/日志/链路，字段没有证据时标未知。接入向导按当前工作负载 metricsPath、业务端口、采集方式解释，不能把未上报 RED 当作 0 请求/0 错误。

保留 TraceID 精查完整已返回 span、孤立 span 与日志关联；明确“已返回的 span”不等于业务所有服务已埋点。树缺父节点、时间不一致、关联日志读取失败各自解释；候选列表 100 条的当前提示保留。TraceID 与严格实体筛选模式的差别保持可见。

告警通知带 rule/alert/target 与时间范围定位到对应实体；如现通知只具 targetId 不能补造规则/TraceID。首页将事件历史和当前待处理区分，无任务状态前称“需关注动态”，不把 severity≠info 当作未处理任务的完整定义。

## 6. 环境与健康矩阵

环境目录与工作负载统计分别取数；统计失败显示未知而非“空闲/正常”。健康算法按 Deployment/Job/CronJob 区分，完成 Job 不按 Deployment ready/replicas 判坏；对象归属与数据时间可检查。

删除环境先展示实际依赖（工作负载、数据服务、泳道、流水线目标、配置），支持后端预检与冲突阻断。不用多个重复确认弹窗代替依赖检查；若当前语义只是删除元数据必须清楚说明，不能称清理环境。顶栏超时切回“全部”不代表写操作获得或失去后端授权，资源真实环境检查仍必须执行。

## 7. 验收

- 5 项泳道配置第 3 项失败：用户能看到 2 成功/1 失败/2 未执行；原子契约上线后全成功或全回滚；重复提交不重复执行。
- 移除覆盖恢复继承、删除有效 key、提升基线各有独立预览，Secret 不出明文；目标变更不串写。
- 发布成功但无客户端回报显示采用未知；启动配置保存后显示待重建，不显示运行已更新。
- Prometheus 全失败、部分失败、成功空集、真实 0、旧数据五种输入有不同状态；其他信号仍可查询。
- 路由保存后下发失败可以定位 controller 证据；enabled 不直接变公网健康。
- 告警到实体日志最多 2 次主要操作，保留环境/泳道/时间范围；精确 TraceID 可独立恢复深链。
- 环境统计接口失败不显示健康；已完成 Job、暂停 CronJob 与未就绪 Deployment 分类正确。
