## 0. 长久思考的提示词

本节是整个终点架构的「宪法」。无论未来谁（人或 AI）来改 console-user，先把这组问题跑一遍。它们不随版本过时——因为问的不是「做什么」，而是「凭什么加东西」。

### 0.1 五问过滤器（每个新概念/新入口/新层级必须全过）

1. **删了它会死吗？** 不进用户词典这个功能就不能用，才算必需。只是「有人可能想看」的，进「更多」或不做。
2. **新手前 5 分钟能躲开它吗？** 首次部署路径上每出现一个新名词，完成率掉一截。进阶能力必须做到：不用它也能走完主路径。
3. **它替谁把关？** 管控类设计先回答「保护谁、防谁」。答不出具体受害场景的管控，是给管理员的安全感税，删。
4. **它和已有词同姓吗？** 同名不同物是最大的认知税（三个「服务」的教训）。新词进词典前查重：组织内已有一个字面相近的用户词，就必须改名或合并。
5. **一年后它是什么？** 现在为 3 个产品设计的层，在 30 个产品时是助力还是废墟？只服务当前规模的设计要标注「临时」，不许悄悄变永久。

### 0.2 规模预演（每次 IA 改版跑一遍）

在 1 / 10 / 100 个产品三种规模下，分别回答：

- 登录第一屏，用户要扫过多少行才找到自己的产品？
- 一个服务挂了，从「看到红色」到「看到日志」是几跳？
- 新人从入职到完成第一次部署，要被教几个词？

任何规模下答案变差的设计，是给未来埋的雷。

### 0.3 简单度回归验收（每次改版必须全绿）

- [ ] 必学名词 ≤ 4 个（组织 / 产品 / 服务 / 环境），其余全部「用到才出现」
- [ ] 首条服务可访问 ≤ 5 步，每步最多引入 1 个新概念
- [ ] 每屏最多 1 个主按钮；主按钮永远是「当前上下文最可能的下一步」
- [ ] 环境只在一处切换（顶栏）；不出现「先选环境再找产品」的树
- [ ] 所有列表页行可点，点进去的页有明确的「返回上一层」

## 1. 北极星

用户面只认四层：

**组织 → 产品 → 服务 →（环境 × 泳道）上的运行**

- **组织**：谁家的云（今天的租户；登录、隔离、计费）。用户词典说「组织」，不说「租户」。
- **产品**：命运共同体——一起活、一起发、共享库和成员（今天的「应用」，不再当可部署物）。**产品是边界，不是可部署的东西。**
- **服务**：真正能部署、能访问、能扩缩、能看日志的东西（`internal/service` 的 Service：web / backend / agent / static / cron）。**服务是运行的主语。**
- **环境 / 泳道**：同一个服务跑在哪。环境是维度（顶栏切换器），不是再复制一套产品树。泳道是高级能力，藏在服务详情里。

**一句话画像（重构成什么样子）：**
登录就是产品列表；点开产品就是服务表；点开服务就能看到实例、域名、日志和一个「部署」按钮。环境是顶栏的一个切换器。其他一切——构建、镜像、泳道、治理、密钥、AI 资产——都长在「到达它们的路上」，而不是站在导航里等你路过。

**首路径减负（对抗自检修补）：**「新建产品→新建服务」两步对新手是纯开销。创建服务时若尚无产品，提供**内联新建产品**（同一张表单的上半段，产品名默认填服务名），四层模型不变、首路径省一步。

**可量化验收**（拍板后作为体验回归基线，沿用 §0.3）：

| 指标 | 现状 | 终点 |
|------|------|------|
| 首条服务可访问 | 约 14 步（冷启动审计） | ≤ 5 步 |
| 必学名词 | 约 20 个平级词 | 4 个 + 用到才出现 |
| 应用详情 | 15 tab | 3 面（服务 / 交付 / 设置） |
| 侧栏一级入口 | 4 主操作 + 5 分组约 20 项 | 2 项（首页 / 产品）+「更多」 |

## 2. 现状事实

调研走查以 `2026-09-06-console-user-ia-destination.md` §2 为准（2026-09-07 复核：console-user 导航与视图自 09-06 走查后无改动，事实仍成立）。对拍板起决定作用的事实摘要：

- 登录页套完整控制台壳（侧栏 + 顶栏 + 未登录状态并存）。
- 应用详情 15 个 tab；默认 tab 与顶栏抢首屏。
- 侧栏「应用 / DevOps / Playground / 模型市场」主操作 + 资源中心 / 工作负载 / AI 服务 / 平台能力分组，约 20 个平级入口。
- 三个「服务」同天出现：服务模型 Service、治理 Service、侧栏工作负载组里的「服务」。
- 应用列表渲染副本 / 请求秒等「像可部署物」的信号。
- 简单度 6.0 的根因是**概念平铺**，不是样式密度——只改皮肤不砍概念，劝退点原样在。

## 3. 否决记录

继承 09-06 版五条否决（证据见原文件 §3），结论不变：

1. **只改样式概念不动**——好看但劝退点原样在；壳层手法降级为实施第一刀。
2. **整页抄 OnePaaS 产线树（产线→产品→应用三层必经 + 三层成员/卡点/SOP）**——第一用户是开发者不是产线负责人；4~10 个产品的组织会被逼出「一线一品」空文件夹；三层成员是管控税。
3. **服务当顶层（Heroku「App=可部署物」）**——多服务产品（paas-shop 五服务 + 共享库 + 发车）会失去归属层，最后必然再发明一个「项目」。
4. **把「应用」改造成组织/部门树**——组织已是租户，部门树与「共享库+发车」不是一层。
5. **Backstage 必经「域→系统→组件」**——中小私有化没有「域」口语。

本版新增否决：

6. **否决「工作台」作为一级概念。** 09-06 版设计了组织工作台（待办聚合 + 产品列表）作为登录默认页。重裁：待办有价值，但「工作台」本身是个要学的新词，且它会和「产品列表」争夺首页身份。**终点：登录直接落产品列表，待办是列表页顶部的一条窄横幅**（失败 N / 待审批 N 胶囊，点开抽屉）。功能等价，少一个一级概念。
7. **否决「团队」实体进本期。** 09-06 版把团队画为「人的家（正交）」。重裁：团队解决的是组织规模化后的人分组，本期没有这个规模（YAGNI）。工种人选直接用组织成员。产品多、人多到名单扫不动时再立项，届时它只是工种表选人器的数据源变化，不动 IA。
8. **否决「产线」任何形式的实体化（含可选目录）。** 09-06 版保留「产线=可选目录」。重裁：本期连可选也不做。产品多到扫不动的真实场景出现时，先用产品排序/置顶/标签过渡；正式产线层等真实付费用户提出再立 spec。**管控层没有真实用户之前不做，是「简单好用」的硬约束。**

## 4. 终点形态

```
组织                          登录隔离计费（用户词：组织）
│
└── 产品                      命运共同体：共享资源、薄授权、整单发车
      └── 服务                运行主语：仓库、实例、域名、日志、工种
            └── 运行 = 服务 × 环境 × 泳道（环境=顶栏维度，泳道=服务内高级）
```

规则（继承 09-06，表述收紧）：

1. 环境不是父亲：不存在「先选生产再看一套产品副本」。产品与服务各定义一次，环境只是切换器。
2. 本期四层之外没有任何父亲层（无产线、无域、无部门树）。
3. 后端表名（`applications` / `tenant_id`）与 API 路径（`/api/applications`）**全部不动**。本期改的只是用户词、导航与信息组织。这是「简单」路线的工程学保障：把认知重构与存储重构解耦，认知先行。

每层只回答一个问题：

| 层 | 用户问的 | 打开看见 | 主按钮 |
|----|----------|----------|--------|
| 组织（首页） | 我的产品都还好吗 | 产品表 + 待办横幅 | 新建产品 |
| 产品 | 这事做得怎样 | 服务表 + 最近交付 | 新建服务 / 去处理失败 |
| 服务 | 它能不能用 | 当前环境实例/域名/日志 | 部署到当前环境 |
| 运行（下钻） | 这次为什么挂 | 副本、事件、日志 | 看日志 / 重试 |

**用户每天说的：** 组织、产品、服务、环境、运行、日志、域名、部署（动词）。

**多人协作才说的：** 变更、发车、评审、金丝雀。

## 6. 人岗：默认最简，按需解锁

原则：**默认态一个 Owner 全兼；复杂度随团队规模按需解锁，而不是默认摆出全套。**

### 6.1 角色挂哪层（业界收敛：挂在离工作最近的一层）

```
组织级：账号 + 全局底线（tenant-admin / developer / viewer，现状 RBAC 不动）
产品级：薄授权 —— 管理员 / 发布 / 派生成员（三行，永不加厚）
服务级：工种表 —— Owner / PE / DEV / TEST（用户每天改的表）
```

- GitHub 把角色挂仓库、K8s 把 RBAC 挂 namespace——权限挂在离工作最近处，人先归组织。本设计同构。
- **禁止**在产品层再放一套工种（OnePaaS 三层成员之鉴）；**禁止**角色随环境翻倍（DEV 在测试和生产是同一个 DEV，差异用「角色 × 环境写权限」矩阵表达）。

### 6.2 服务工种 × 环境写权限矩阵

| 工种 | 是谁 | 测试环境写 | 生产环境写 | 管本服务工种 |
|------|------|-----------|-----------|--------------|
| Owner | 服务负责人 | ✓ | ✓ | ✓ |
| PE | 生产/稳定性 | ✓ | ✓ | — |
| DEV | 开发 | ✓ | — | — |
| TEST | 测试/验收 | ✓（验证） | — | — |

- 同一角色可多人；同一人可跨服务跨角色。
- 「测试同学不能发布生产」= DEV/TEST 的生产写禁止；不再依赖产品级 `Restricted` 开关。它能表达「bff 的 TEST 不是 chatbot 的 TEST」——这是现状应用级成员模型表达不了的。
- 底层机制复用现状 `prod:write` + `EnvTypeResolver` fail-closed：Owner/PE 映射到 prod:write，DEV/TEST 不映射。RBAC 网关仍是全局底线。
- 工种人选 = 组织成员（本期无团队实体，见 §3 否决 7）。

### 6.3 产品薄授权（跨服务的事）

| 产品角色 | 干什么 | 来源 |
|----------|--------|------|
| 管理员 | 加服务、绑共享资源/密钥、改产品设置 | 默认由创建者兼 |
| 发布 | 批整单发车 / 批次 | 指定一人，常为某 Owner |
| 成员（派生） | 能看见该产品 | 任一服务工种自动获得，不加第二遍 |

### 6.4 与现状应用成员的迁移（两期制，风险隔离）

现状 `owner/maintainer/developer/viewer` + `Restricted` 是**产品级**授权；终点把「能否发布这个服务」下沉到工种。这是授权模型变更，不是文案变更，**必须与词面/导航改造分期**：

- **第一期（本 spec 落地范围）：权限模型完全不动。** 现状应用成员继续生效，仅改词展示（「应用成员」→「产品成员」）。零迁移风险拿到 80% 的简单收益。
- **第二期（单独 spec + 单独评审）：工种下沉。** 迁移映射：应用 owner→产品管理员、maintainer→各服务 Owner、developer→DEV、viewer→派生成员；`Restricted` 语义并入角色×环境矩阵后退役。双轨期必须有明确切换点，禁止两套并行判断。

## 7. 密钥与配置（用户词，不新增实体层）

| 挂哪 | 什么 |
|------|------|
| 组织 | 全组织共用（推理网关、镜像仓库） |
| 产品 | 这窝服务共用（库/缓存/MQ） |
| 服务 | 只有自己该有的（JWT、模型凭证） |

配置三词（不合并存储，设置里分三块互链）：

| 现名 | 用户词 | 一句话 |
|------|--------|--------|
| appconfig | 运行配置 | 启动注入，改完重启/重发 |
| configcenter | 动态配置 | 热更新，带版本 |
| Secret | 密钥 | 被引用的凭证 |

产品密钥明文可见：产品管理员 + 各服务 Owner/PE；DEV/TEST 默认掩码。

## 8. 与 OnePaaS 对照

证据文件（09-06 版 §8 已核实，本版沿用）：`onepaas-appcenter/entity/app.go`、`constant.Role*`、`pkg/entypes` ResType、`app-center-assets` 产线/产品同套 Tab、`appcenter-resource` 策略存储。

| OnePaaS 做法 | 本终点 | 理由 |
|--------------|--------|------|
| 叶子叫「应用」 | 不采用 | 中文歧义；我们已有 Service 实体当主语 |
| 产线必有且养成员/卡点/SOP | 不采用 | 开发者主路径不能先过产线 |
| 产线、产品各克隆一套设置 | 不采用 | 认知税；产品少时一线一品更差 |
| 三层各养 Owner/PE/DEV/QA | 不采用 | 工种只在服务；产品薄授权 |
| 上层非空覆盖下层卡点 | 不采用为默认 | 老人能玩新人必懵 |
| 生效来源写在脸上 | **采用（原则）** | 任何未来默认策略须标明来源层 |
| Owner 移交一等动作 | **采用** | 产品管理员/服务 Owner 可移交，记审计 |
| 人与策略分存 | **采用（原则）** | 策略不塞进产品大结构体 |
| 成本团队 ≠ 授权成员 | **采用** | 与「成员在组织、工种在服务」一致 |
| 白名单只能由上层加 | **采用（原则）** | 自己不能免自己 |
| 资源概览看板 | **采用** | 产品看占用、服务看实例 |
| SOP/OPA 平台 | 不采用为必经 | 可执行检查可薄做，不上 OPA |
| 虚拟产品 VPD | 不采用 | 变更批次已覆盖跨服务发车 |

**先进性共识（写进拍板记录）：** 治理引擎 OnePaaS 更深；运行模型（服务×环境×泳道、多租户、AI 运行时）本平台更深。用户面赢在少概念，不赢在设置页份数。

## 9. 控制台线框

不换皮肤（暗色、`--brand`、生产红沿用）。以下为结构，非视觉稿。

### 9.1 登录（无壳）

```
全屏，无侧栏无顶栏
[P] 组织名        登录
                  用户名 / 密码 / 登录
                  演示账号（仅 demo）
```

`meta.public` 不渲染 App 壳；失败统一「用户名或密码错误」。

### 9.2 壳

```
┌ 248px ────────┬ 顶栏 48px ─────────────────────────────────────┐
│ 首页(产品) ●  │ 上下文标题   [环境 ▾]   🔔   ⌘K   [用户 ▾]   │
│ ── 更多 ▾     │ 搜索收成按钮；主题进用户菜单；单一头像；       │
│   模型/试玩   │ 生产倒计时只在环境芯片里                        │
│   数据服务    │                                                │
│   流量        │                                                │
│   可观测      │                                                │
│   密钥        │                                                │
│ 环境（管理）  │                                                │
│ 组织设置      │                                                │
└───────────────┴────────────────────────────────────────────────┘
```

- 侧栏一级只有**首页（=产品列表）**与**更多**。无「工作台」、无「DevOps」、无「工作负载」组。
- DevOps 值班台并入首页待办横幅；档案（运行列表/变更/构建史）从首页待办或产品「交付」进入。

### 9.3 首页 = 产品列表 + 待办横幅

```
⚠ 失败 2 · 待审批 1        （点开抽屉：按产品分组的待办，直达运行/审批）
产品
  商城      5 个服务   测试 5/5   生产 4/5   3 分钟前发车失败
  智能客服  2 个服务   测试 2/2   生产 —    空闲
                                              [新建产品]
```

禁止假指标卡墙（健康/副本/请求秒）。行点击进产品。

### 9.4 产品（默认：服务表）

```
← 首页 / 商城                        [健康]     ⋯
┌ 服务 ● ┬ 交付 ┬ 设置 ┐
服务       类型      本环境      域名          下一步
frontend   web       测试 1/1   shop.test     日志
bff        backend   测试 1/1   bff.test      日志
chatbot    agent     测试 0/1   探活失败       看运行
                                             [新建服务]
```

- **服务**：默认面。环境信号只看顶栏 + 每行的「本环境」列。
- **交付**：流水线 / 运行 / 变更 / 发车（进阶，不拦首发）。失败待办直达 `/devops/runs/:id`。
- **设置**：共享资源、运行配置、动态配置、密钥引用、薄授权、用量。
- `?tab=` 深链兼容：旧 `tab=builds` 打开「交付」并定位档案。
- 身份条不展示「应用.env」。

### 9.5 服务（运行主语）

```
← 商城 / bff          [Owner 张三 · PE 李四 · DEV 2 · TEST 1]
本环境：测试 ●                （顶栏切到生产即看生产）
实例 1/1    域名    日志    [部署]    ▸ 高级（泳道/流量/告警规则）
工种管理    私有密钥    本服务运行配置
```

部署是按钮，不是并列 tab。泳道在「高级」折叠组里。

### 9.6 待办抽屉（原值班台）

```
失败待处理              等待决策              进行中
商城 · CI 失败 3 分钟前  商城 · 待审批 12 分钟  hello · 部署中 40 秒
[看日志]                [去审批]              [看运行]
```

三列；审批与评审用 tag 区分。档案室降为交付面分段，不占一级页签。**抽屉底部固定「查看全部运行」出口**（运维老人的历史检索习惯不被待办截断）。

## 13. 落地顺序（两期制）

**第一期（词面 + 导航 + 三面；不动权限、不动存储）——本 spec 拍板即可开工：**

1. 登录无壳；顶栏去重（48px、去双头像、搜索收按钮）。
2. 侧栏收敛：首页（产品列表）+ 更多；删工作负载组、DevOps 一级、Playground 降级。
3. 应用→产品改词 + 六面对账（UI/审计/OpenAPI/文档站/示例/CLAUDE.md）；列表去假指标。
4. 产品三面（服务/交付/设置）替换 15 tab；`?tab=` 兼容。
5. 首页待办横幅 + 抽屉（数据源=现有 `/api/notifications`，先做只读聚合，不新建持久化）。
6. 治理改称「流量」；appconfig/configcenter/secret 改三词。

**第二期（授权模型下沉；单独 spec + 评审后开工）：**

7. 服务工种表 + 角色×环境写权限矩阵 + 产品薄授权。
8. 现状应用成员迁移映射与 `Restricted` 退役；双轨切换点。

**节奏理由：** 第一期 6 步全是词面/导航/聚合层改动，风险低、简单收益立即可见；第二期是授权模型变更，必须隔离评审。第 1~2 步甚至不依赖本 spec 全部拍板（壳层手法早已是共识），可先行。
