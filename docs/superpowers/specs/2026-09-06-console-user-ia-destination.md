# console-user 终点信息架构

> 日期：2026-09-06  
> 范围：仅 **console-user** 用户面信息架构（概念、导航、人岗）。不改 console-admin。  
> 状态：**待评审**。本文件是终点提案，不是已实施设计，也不是已签字的「已定架构」。  
> 对照：现网 `http://paas.k8s.dd/console/`、`frontend/console-user`、服务模型 spec `2026-08-19-service-model-design.md`、业界评估 `2026-09-02-industry-readiness-assessment.md`、OnePaaS 三仓（appcenter / app-center-assets / appcenter-resource）。  
> 禁区（写 spec 时已遵守）：不改业务代码；产线不是必经层；咨询过但未拍板的能力不写进必经层。

---

## 1. 北极星

用户面只认四层：

**组织 → 产品 → 服务 →（环境 × 泳道）上的运行**

- **组织**：谁家的云（今天的租户：登录、隔离、计费）。
- **产品**：一起活、一起发、共享库和成员的命运共同体（今天用户口中的「应用」，但不再当可部署物）。
- **服务**：真正能访问、能扩缩、能看日志的东西（`internal/service` 的 Service：web / backend / agent / static / cron）。
- **环境 / 泳道**：同一个服务跑在哪。环境是维度，不是再复制一套产品树。泳道默认基线，日常不用先学。

过滤一切新概念的一问：*这件事是否让「第一条服务可访问」更快、更稳、更少名词？*  
主叙事沿用业界评估的品类定位（私有化交付工厂），副叙事 AI 运行时。品类里的「应用」二字不进入控制台用户词。不服务主叙事的能力进「更多 / 设置」，不进默认路径。

可量化（沿用评估、作拍板后的体验验收，不是本文件的实现承诺）：

| 指标 | 现状参考 | 终点 |
|------|----------|------|
| 首条服务可访问 | 冷启动审计约 14 步 | ≤5 步，每步最多引入 1 个新概念 |
| 用户面必学名词 | 约 20 个平级词 | 组织 / 产品 / 服务 / 环境（+ 用到才出现的词） |
| 详情默认页 | 15 tab，默认「服务」与「部署/概览」抢首屏 | 产品页默认服务表；服务页才是运行态 |

## 2. 现状（对照现网与代码，2026-09-04 走查）

### 2.1 用户实际看见的

- 登录仍套完整壳（侧栏 + 顶栏 +「未登录」），表单盖在控制台上。
- 侧栏主操作：应用 / DevOps / Playground / 模型市场；其下资源中心、工作负载、AI 服务、平台能力、环境、设置。
- 应用列表：营销卡（渐变首字、描述、models/mq/dal、副本、请求/秒）。`paas-shop` 显示健康 5/5，详情身份条却出现与顶栏环境不一致的 chip。
- 应用详情：`DetailShell` + **15 个 tab**（运行态：服务 / 概览 / 部署 / 服务治理 / 可观测；资源：资源绑定 / 配置 / 成员与权限 / 用量；DevOps：流水线 / 变更 / 代码仓库 / 构建 / 镜像 / 发布），默认 tab 为「服务」。动态配置嵌在「配置」页内，不另占 tab。
- DevOps：值班台 + 档案室（运行记录 / 变更 / 评审 / 批次 / 构建 / 镜像库 / 发布）。值班台模板四列（失败 / 审批 / 进行中 / 等评审），CSS `repeat(3, 1fr)`，等评审会挤版。
- 顶栏：大标题、铃铛、环境、⌘K、主题、用户芯片、**再叠一个无交互头像**。

### 2.2 代码与模型上的错位

| 事实 | 出处 | 对用户的伤害 |
|------|------|--------------|
| `Application` 仍带 `Env`、`Replicas`、`RPS` | `internal/core/application/model.go` | 应用被画成可部署物，和「应用跨环境」矛盾 |
| 服务实体已存在（web/backend/agent/static/cron） | `internal/service`、`AppServices.vue`、08-19 spec | 正确主语已落地，导航仍把应用当主语 |
| 工作负载仍是侧栏一组 | `App.vue` nav | 与「服务」抢运行态 |
| 治理也叫「服务」 | `internal/governance`、平台能力 | 三个「服务」同天出现 |
| 应用成员是 owner/maintainer/developer/viewer | `internal/core/application/member.go` | 是授权，不是 Owner/PE/DEV/TEST 工种 |
| 配置三套都像「配置」 | appconfig / configcenter / security | 改名问题，不是缺功能 |
| 08-19 用户心智写成「应用 → 服务 → 环境」 | 服务模型 spec | 与本终点「产品 → 服务」冲突，见 §10 |

### 2.3 诊断（不是样式问题）

只改密度和皮肤，用户仍要同时学：应用、服务、工作负载、治理服务、部署、环境、泳道、流水线、变更、批次、构建、镜像、发布、配置、配置中心。  
业界评估「体验 6.5 / 简单度 6.0」的根因是**概念平铺**，不是配色。

## 3. 备选与否决

终点必须先否决错误形状，再画对的。下列三项**否决**，不进入拍板范围。

### 3.1 否决：只改样式，概念不动（原「方案 B 危险落地」）

把 15 tab 收成三个模式、列表改密表、登录无壳，但「应用 / 工作负载 / 治理服务」仍平级出现。  
**否决理由**：现网最大税是同名不同物，不是卡片圆角。做完会更好看，劝退点原样在。壳层手法（顶栏 48px、去双头像）可以当**实施第一刀**，不能当产品决策。

### 3.2 否决：整页抄 OnePaaS（产线 → 产品 → 应用 + 三层成员/卡点/SOP）

OnePaaS 产线详情与产品详情是同一套 Tab：成员、质量卡点、SOP、白名单、资源概览；应用再跟一套。合并规则「产线 > 产品 > 应用」，下层要自己定必须进上层白名单。  
**否决理由**：

- 我们的第一用户是应用开发者，不是产线负责人。产线必经会把 4～10 个产品的组织逼出「一线一品」空文件夹。
- 三套成员 + 三套策略是管控深度，不是开发者好用。会丢掉我们相对 OnePaaS 唯一能赢的东西：少一层、服务当主语、默认就能发。
- 本文件禁区已写明：**产线不是必经层**。

OnePaaS 仍有可借用点，见 §8，不等于抄树。

### 3.3 否决：杀掉分组，服务当顶层（Heroku「App = 可部署物」）

侧栏直接是服务列表，不再有产品。  
**否决理由**：`paas-shop` 已是五服务 + 共享库 + 变更火车。没有分组层，绑定、发车、级联删除会失去归属，最后会再发明一个「项目」。分组要留，只是不再叫可部署的「应用」。

### 3.4 未进入终点的另外两条（一并否决，避免拍板时回潮）

| 备选 | 否决理由 |
|------|----------|
| 把今天的「应用」改成组织/部门树 | 组织已经是租户。部门树和「共享库+发车」不是一层。 |
| Backstage 必经「域 → 系统 → 组件」 | 中小私有化没有「域」口语。域若出现，只当产品多了之后的可选目录，与产线同级策略。 |

## 4. 终点分层（拍板对象）

用户面必学主叙事仍是四层（组织 → 产品 → 服务 → 环境）。团队与产线画在旁边，避免被误读成第五、第六个必经父亲。

```
组织                         登录隔离计费；对外不说「租户」
│
├── 团队                     人的家（正交，不是树上必经节点）
├── 产线（可选目录）         产品多到扫不动才露；不养人、不发车、不配密钥
│
└── 产品                     命运共同体：共享资源、薄授权、整单发车
      └── 服务               运行主语：仓库、端口、实例、域名、工种
            └── 运行 = 服务 × 环境 × 泳道
```

规则：

1. 环境**不是父亲**。不要做成「先选生产再看见一套产品副本」。产品和服务各定义一次。
2. 产线可以没有。没有产线时，产品直接挂在组织下。禁止强制「默认产线」。
3. 团队不插入「组织 → 团队 → 产品」的必经路径。一个团队可负责多个产品；一个产品有一个负责团队。
4. 后端表名可以继续叫 `applications` / `tenant_id`。改的是**用户词和导航主语**，不是先翻存储。

每层只回答一个问题：

| 层 | 用户问的 | 打开看见 | 主按钮 |
|----|----------|----------|--------|
| 组织 | 我在哪家 | 产品列表 + 待办 + 用量 | 新建产品 |
| 产品 | 这事做得怎样 | 服务一览、共享资源、最近发车 | 新建服务 / 去处理失败 |
| 服务 | 它能不能用 | 各环境实例、域名、日志、最近运行 | 部署到当前环境 |
| 运行 | 这一次为什么挂 | 副本、事件、日志 | 看日志 / 重试 |

## 5. 概念表（留 / 藏 / 改名）

**留** = 用户每天看见或用到就看见。  
**藏** = 实现保留，导航与文案不对用户说。  
**改名** = 实体可留，用户词必须换。

| 今天的词 / 实体 | 处置 | 终点用户词 | 说明 |
|-----------------|------|------------|------|
| 租户 Tenant | 改名 | 组织 | 房子；不部署 |
| 应用 Application | 改名 | 产品 | 边界，不是可部署物。列表禁止再渲染副本/RPS |
| Application.Env / Replicas / RPS | 藏 | — | 字段可暂留，用户面删除 |
| 服务 Service（web/backend/…） | 留 | 服务 | 主语 |
| 工作负载 Workload | 藏 | 运行 / 实例 | 服务在某环境×泳道的实例化 |
| 侧栏「工作负载」 | 藏 | — | 整组从侧栏拿掉，由服务下钻 |
| 部署 tab | 藏（并入服务） | — | 环境和实例是服务的谓语 |
| 治理 Service | 改名 | 流量 | 发现 / 域名 / 熔断；派生自服务，不再叫服务 |
| 环境（顶栏） | 留 | 环境 | 唯一切换（操作面） |
| 环境（侧栏菜单） | 留 | 环境（管理） | 只进 CRUD/详情，不切换 scope |
| 泳道 | 留（降级） | 泳道 | 从服务/环境钻入；不进侧栏主操作 |
| 流水线 / 运行 | 留（交付面） | 运行 / 流水线 | 日常盯运行 |
| 构建 / 镜像 / 发布 | 藏（降级档案） | — | 排障时从运行点进去 |
| 变更 / 批次 / 评审 | 留（进阶） | 变更 / 发车 | 产品「交付」里，不拦首发 |
| appconfig | 改名 | 运行配置 | 启动注入，改完要重启 |
| configcenter | 改名 | 动态配置 | 热更新 + 版本 |
| security Secret | 改名 | 密钥 | 被引用的凭证；组织/产品/服务三级挂法见 §7 |
| 资源绑定 | 留（设置） | 共享资源 / 绑定 | 产品设置，不是主 tab 墙 |
| 数据服务 6 Kind | 留（更多） | 数据服务 | 附件，不是主操作 |
| 模型市场 / Playground | 留（更多） | 模型 / 试玩 | 能力调用，不与产品抢侧栏第一屏 |
| AI 编排 7 件套 | 留（更多） | Agent 资产 | 与「服务类型 = agent」区分：一个是跑着的服务，一个是编排资产 |
| 可观测 | 留（下钻） | 可观测 | 从失败/服务进，侧栏进「更多」 |
| 用量 / 成员 | 留（设置） | 用量；人岗见 §6 | 产品设置 |
| Binding / Image / Stage / CRD | 藏 | — | 实现词 |

**用户每天说的：** 组织、团队、产品、服务、环境、运行、日志、域名、部署（动词）。  
**用到才说的：** 泳道、流水线、发布、运行配置、动态配置、密钥、数据服务、流量、可观测。  
**多人协作才说的：** 变更、发车、评审、金丝雀。  
**禁止再教的：** 应用（作用户面主语）、工作负载、治理服务、租户、Binding。

## 6. 人岗（团队 vs 服务工种）

两套东西，禁止做成两份同构花名册。

### 6.1 人在哪

| 放哪 | 是什么 |
|------|--------|
| 组织 | 能登录的账号 |
| 团队 | **成员的家**（商城组 = 一组人） |
| 产品 | **不自建通讯录**。挂一个负责团队；薄授权见下 |
| 服务 | **工种表**：Owner / PE / DEV / TEST，人选来自团队（或组织账号） |
| 产线 | **零人员、零团队名单** |

产品成员默认推导：在该产品任一服务上有工种 → 自动能进产品，不必加两遍。

### 6.2 服务工种（用户每天改的表）

与 OnePaaS 应用角色（Owner/PE/DEV/QA/…）同构的是**这一层**，不是产品层。本终点收敛为四种（不照搬 SQA/OPS/Reviewer/DBQuery，避免工种膨胀）。

| 角色 | 是谁 | 测环境 | 该服务生产 | 改本服务工种名单 |
|------|------|--------|------------|------------------|
| Owner | 服务负责人 | 能 | 能 | 能 |
| PE | 生产 / 稳定性 | 能 | 能 | 否 |
| DEV | 开发 | 能 | 否 | 否 |
| TEST | 测试 / 验收 | 能（验证） | 否 | 否 |

- 同一角色可多人；同一人可跨服务、跨角色。
- 门禁：动**这个服务**的生产看 Owner/PE；开**整列火车**看产品「发布」。
- 这与现状 `app-owner / app-maintainer / app-developer / app-viewer` **不是同一张表**。现状是产品（今「应用」）级授权；终点把「能不能发布这个服务」落到工种，把「能不能开整单」留在产品薄授权。映射在实施计划里做，本文件不规定 migration 步骤。

### 6.3 产品薄授权（跨服务的事）

| 产品角色 | 干什么 | 典型来源 |
|----------|--------|----------|
| 管理员 | 加服务、绑共享库/密钥、改产品设置 | 常由各服务 Owner 兼，或负责团队指定 |
| 发布 | 批整单发车 / 批次 | 指定一人，常为某 Owner |
| 成员（派生） | 能看见该产品 | 任一服务工种自动获得 |

产品**不再**放一套 Owner/PE/DEV/TEST。工种只在服务上。

### 6.4 和现状应用成员的关系（避免拍板误解）

今天 `Restricted` + 应用成员解决的是「测试人员不能发布」。终点用服务 TEST 不能写生产、产品「发布」才能发车，覆盖同一诉求，且能表达「bff 的 TEST 不是 chatbot 的 TEST」。  
`Restricted` 开关本身不是用户面名词；实施时可变成「启用产品内权限」类设置，本文件不展开交互稿。

## 7. 密钥与配置（用户词，不是新实体层）

### 7.1 密钥挂载

| 放哪 | 什么 |
|------|------|
| 组织 | 全组织共用（推理网关、镜像仓库） |
| 产品 | 这窝服务共用（库 / 缓存 / MQ） |
| 服务 | 只有自己该有的（JWT、模型凭证） |

服务配置引用产品密钥，不复制明文。谁能看产品密钥明文：产品管理员 + 各服务 Owner/PE；DEV/TEST 默认掩码。  
实现上已有 `security` 与 appconfig，本层只规定**用户挂在哪、叫什么**。

### 7.2 配置三词

| 现名 | 用户词 | 一句话 |
|------|--------|--------|
| appconfig | 运行配置 | 启动注入，改完要重启/重发 |
| configcenter | 动态配置 | 热更新，带版本 |
| Secret | 密钥 | 被引用的凭证 |

不合并三套存储。产品「设置」里分三块并互链。

## 8. 与 OnePaaS 对照

证据来自：

- `onepaas-appcenter`：`entity/app.go`（产线/产品/应用、ProductLineUsers/ProductUsers）、`constant.Role*`、`pkg/entypes` 的 `ResType`（app / product-line / product / vpd）、`feature/resourcesrv/quliaty.go` 合并与白名单。
- `onepaas-app-center-assets`：产线/产品详情同一套 Tab；应用设置含质量卡点与 SOP；文案「产线 > 产品 > 应用」。
- `onepaas-appcenter-resource`：`kind + name + payload` 存策略，不管人。

他们的树：**产线 → 产品 → 应用**。叶子「应用」= 我们的「服务」（可部署）。成本团队（`org_team_id` / 三级组）与 RBAC 成员拆开。虚拟产品 VPD 跨树捆应用。

| OnePaaS 做法 | 本终点 | 理由 |
|--------------|--------|------|
| 叶子叫「应用」 | 不采用 | 中文里应用既像 App 又像一筐服务；我们已有服务实体 |
| 产线必有且养成员/卡点/SOP | 不采用 | 禁区；开发者主路径不能先过产线 |
| 产线、产品各克隆一套设置页 | 不采用 | 认知税；产品少时一线一品更差 |
| 上层非空覆盖下层卡点 | 不采用为默认 | 老人能玩、新人必懵。若以后做组织默认策略，用「只加严」+ 标明来源 |
| 三层都养 Owner/PE/DEV/QA… | 不采用 | 工种只在服务；产品薄授权；产线零人员 |
| 生效来源写在脸上 | **采用（原则）** | 任何以后挂上的默认策略都须标明来自组织 / 产品 / 本服务；不因此把卡点做成必经 |
| Owner 移交为一等动作 | **采用** | 产品管理员、服务 Owner 可移交，记审计 |
| 人与策略分存 | **采用（原则）** | 人是 RBAC；策略若做，不塞进产品大结构体 |
| 成本团队 ≠ 授权成员 | **采用** | 与 §6「成员在团队」一致 |
| 白名单只能由上一层加 | **采用（原则）** | 自己不能免自己；本文件不把卡点做成必经能力 |
| 资源概览当看板 | **采用** | 产品看占用，服务看实例；产线以后做汇总 |
| SOP/OPA 平台 | 不采用为必经 | 可执行检查可薄做（见 §12），不上 OPA 宇宙 |
| 虚拟产品 VPD | 不采用新词 | 变更批次已覆盖跨服务发车 |
| 双树（产线树 + 组织树） | 不采用为默认 | 组织工作台 + 产品列表足够；组织树是管理面 |

**先进性一句话（写入拍板共识，避免事后争论「谁更先进」）：**  
治理引擎 OnePaaS 更深；运行模型（服务 × 环境 × 泳道、多租户、AI 在主叙事）本平台更深。用户面要赢在少概念，不赢在设置页份数。

## 9. 控制台信息架构线框

### 9.2 壳

```
│   流量        │                                                 │
```

- 「工作负载」组删除。
- 环境菜单 = 管理面，与顶栏 scope 分工沿用 `2026-07-28-environment-ia-redesign.md`。

### 9.3 组织工作台（登录后默认）

```
待办     失败 2    待审批 1
产品
  商城      5 个服务   测试 5/5   生产 4/5    3 分钟前发车失败
  智能客服  2 个服务   测试 2/2   生产 —      空闲
```

禁止再做「健康 / 副本 / 请求秒」假指标卡墙。行点击进产品。

### 9.4 产品（默认：服务表）

```
← 工作台 / 商城                    [健康]     ⋯
┌ 服务 ● ┬ 交付 ┬ 设置 ┐
服务       类型      本环境        域名            下一步
frontend   web       测试 1/1      shop.test       日志
bff        backend   测试 1/1      bff.test        日志
chatbot    agent     测试 0/1      探活失败        看运行
```

- **服务**：上表。从工作台进产品落这里。
- **交付**：流水线 / 运行 / 变更 / 发车（进阶）。从失败待办进可落到交付或直达 `/devops/runs/:id`。
- **设置**：共享资源、运行配置、动态配置、密钥引用、负责团队、薄授权、用量。
- 身份条不展示「应用.env」。环境只看顶栏。
- `?tab=` 深链保留：旧 `tab=builds` 打开「交付」并定位构建/运行档案，不废链接。

### 9.5 服务（运行主语）

```
← 商城 / bff     [Owner 张三 · PE 李四]
本环境 测试 ●     生产
实例 1/1    域名    日志    部署（按钮）
工种：Owner / PE / DEV / TEST
私有密钥、本服务运行配置
```

部署是按钮，不是和「服务」并列的第四个顶级 tab。

### 9.6 工作台待办（原 DevOps 值班台）

```
失败待处理          等待决策              进行中
商城 · CI 失败      商城 · 待审批         hello · 部署中
3 分钟前            12 分钟前             40 秒前
[看日志]            [去审批]              [看运行]
```

三列：失败 / 等待决策（审批+评审用 tag 区分） / 进行中。档案室降为工作台或产品交付里的分段，不与待办抢 8 个大页签。

## 12. 未拍板（咨询过，不进必经层）

下列在讨论中出现过，**不是本终点的成立条件**。拍板本文件时既不必实现，也不得当成「已经定了」。

| 项 | 讨论时的倾向 | 为何不写进必经 |
|----|--------------|----------------|
| 产线负责人 / 产线 PE | 仅当产线要管预算或默认门禁时才值得有岗 | 一挂人，产线就变成第三套组织 |
| 产品 PE（独立岗） | 可能与「发布」重复 | 各服务已有 PE |
| 质量卡点 / SOP / 白名单 | 若做：挂产品执行、组织给默认、上层才能开例外、生效来源可见 | OnePaaS 证明大厂有用；抄三层会毁简单度 |
| 资源概览独立成「产线标配页」 | 产品/服务用看板即可 | 产线未成为必经时，线级汇总无对象 |

若后续要做卡点：单独开 spec，遵守 §8「采用」行（来源可见、只加严、上层加例外），且不得回潮成产线必经。

## 13. 建议落地顺序（实施时另开 plan，此处只防拍板后不知从哪刀）

6. 工作台吞入值班台。
