## 平台缺陷（本次旅程发现，按严重度）

### F1（Critical，阻断）：流水线 deploy 不读服务实体 → port/serviceId 永远空
- 根因：`pipeline.Releaser.Deploy` 接口无 `serviceId` 参数（`engine.go:50`），`execDeploy` 只透传 `params.service/port`；而默认绑定 pipeline（OnAppCreate）**不写任何 paramOverrides** → 首次部署 Workload 必然 port=0 → 不建 K8s Service → 冒烟必败 + 服务不可达。
- 服务模型 Phase 1 的 `ServiceDef.Port` 回填（`pg/store.go:768`）只在手动 Release API 路径生效，流水线路径断链。
- **叠加死锁**：`CreateRelease` 复用既有 Workload 时忽略 port（语义合理），但首次 workload 由流水线以 port=0 创建 → 用户无 UI 途径修复（服务编辑不含部署参数重放）。
- 修复方向：`execDeploy` 解析 `params.serviceId`；缺省时若 app 恰有 1 个服务实体自动采用（单服务应用零操作）；`Releaser.Deploy` 加 serviceID 入参；`svcLookup` 链路已就绪，纯粹是接口没接。

### F2（Important）：冒烟默认探活 `/healthz`，但静态页应用没有 healthz
- tpl-ci v2 改成 `/healthz`（K8s 惯例），但 Web/static 类服务（nginx 静态页）无此路径 → 即使 port 打通也必败。
- 修复方向：探活路径按服务类型默认（static → `/`；web/backend → `/healthz` 失败自动降级 `/`）；或探活失败时给出「如何修」的行动提示。

### F3（Important）：CI 流水线无「运行」按钮
- 全部流水线区 CI 只有 编辑/删除，CD 才有「运行」。用户想直接跑一次构建部署（不经变更火车）无入口——火车模型是高级流程，不该是唯一路径。

### F4（Minor）：服务创建弹窗仓库下拉空时无创建引导
- 下拉 "No data" 即死路，应内嵌「去绑定仓库」链接或直接弹绑定表单。

### F5（Minor）：新建变更成功后无反馈
- POST 201 但列表未刷新（需手动刷新页面才出现「初始化部署」行）——前端刷新时机 bug。

### F6（Minor）：冒烟失败错误无下一步指引
- 「探活超时」四个字，未提示「检查服务端口/健康路径」或给出 workload 详情链接。
